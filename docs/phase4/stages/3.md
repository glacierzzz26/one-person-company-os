## 三、实现要点

- **无代码改动**：5 个 Business Capability + 跨 Capability workflow 全部复用现有引擎与模型(3.2 的 (capability, role) 解析、Task 落 capability_id)。
- **两次审批**：approval 门(high, agentless)与 delivery 节点(high, git commit)各触发一次,须分别 approve;reject 审批门 → workflow 中断(delivery 未创建)。承 phase2/3 已知语义。
- **delivery 与已跟踪文件约定**(承 3.3)：`git commit -am` 只提交已跟踪文件的变更。业务产出文件(marketing.md 等)预先 git 跟踪(init 骨架),节点 file-write 改写内容,delivery 提交其变更。
- **quality 角色权限**：delivery 用 git tool,故 quality 除 read/write file 外授予 execute/git。

## 四、冒烟记录

环境：4.1/4.2 的 `/tmp/opos-p4.db`(company `ACME`,5 Business Capability 12 Agent)+ 补 quality execute/git。真实 git 仓库 `/tmp/opos-p4-ws-biz2`(init 预置 README + 5 个业务文件骨架,1 commit)。

1. `os workflow add --name biz-feedback` → `os workflow run`:marketing→sales→customer→operations→finance 完成,approval 门暂停。
2. `os approval approve`(门)→ delivery 节点开始 → 再次暂停(delivery risk=high)。
3. `os approval approve`(delivery)→ `git commit -am "deliver business feedback summary"` → **7/7 nodes completed**,仓库 commit `652a030`,5 个业务文件内容更新。
4. Task 归属核对:6 执行节点 agent/capability 各归其主(见上表)。
5. reject 场景:新 workflow 到 approval 门 → `os approval reject` → `workflow biz-reject aborted at step approval ... rejected by human`,delivery 未创建。
