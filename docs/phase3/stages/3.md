## 一、目标与范围

- 目标：验证 3.1 + 3.2 的成果——产品开发 8 节点流程(Idea→Research→Product Analysis→PRD→Engineering→QA→Approval→Delivery)跨 Research / Product / Engineering 三个 Capability 一键运行，含审批门与失败中断语义。
- 范围：示例 definition `docs/phase3/examples/product-workflow.json`；端到端冒烟。无代码改动(引擎复用 2.2/3.2)。
- 边界：真实 LLM/网络调研仍不做(框架先行，节点内容由流程定义提供)；Business Capabilities 属 Phase 4。

## 三、实现要点

- **无代码改动**：全链路验证 3.2 引擎能力——节点 `capability` 字段驱动 agent 解析与 Task 归属，审批门/轮询/失败中断复用 2.2。
- **两次审批**：approval 门(high, agentless)与 delivery 节点(high, git commit)各触发一次审批，须分别 approve；reject 审批门 → workflow 中断(delivery 未创建)。承 phase2 的已知语义。
- **⚠️ delivery 与「已跟踪文件」约定**：`git commit -am` 只提交已跟踪文件的变更，**不包含未跟踪新文件**。因此：
  - 交付文件须**预先 git 跟踪**(冒烟中 `feature.md` 随 init 提交骨架，engineering 节点再改写内容)；
  - 若流程产出全新文件，需先 `git add`(git tool 白名单支持 add)，或让前置节点产出到已跟踪文件。
  - 归档见「已知问题」。

## 四、冒烟记录

环境：3.1/3.2 的 `/tmp/opos-p3.db` + 补 engineering qa/coding agent + 权限(qa: read/file;coding: read/write/file + execute/git)。真实 git 仓库 `/tmp/opos-p3-ws-prod2`(init 预置 README.md + feature.md 骨架，1 个 commit)。

1. `os workflow add --name product-dev3` → `os workflow run`：research→product-analysis→prd→engineering→qa 完成，approval 门暂停。
2. `os approval approve`(门)→ delivery 节点开始 → 再次暂停(delivery risk=high)。
3. `os approval approve`(delivery)→ `git commit -am "deliver feature"` → **7/7 nodes completed**，仓库 commit `059dee0`，feature.md 更新为 v2。
4. Task 归属核对：7 节点 agent/capability 各归其主(见上表)。
5. reject 场景：新 workflow 到 approval 门 → `os approval reject` → `workflow product-reject aborted at step approval ... rejected by human`，delivery 未创建。
6. ⚠️ 过程中两次失败均为**冒烟脚本缺陷**而非代码缺陷：① 改 Go 后未重建 `bin/os`(见 3.2 归档教训)；② definition 的 `<repo-workspace>` 占位符未替换，产出误写到项目根下 `./<repo-workspace>/`——占位符替换必须到位。

## 五、已知问题 / 待办

- [ ] **新文件交付需 git add**：`git commit -am` 不含未跟踪文件。当前示例靠预置已跟踪文件规避；后续可让 delivery 节点用 `git add` 显式 stage(白名单已支持)，或引入「交付文件清单」声明，属流程完善项。
- [ ] 两次独立审批(approval 门 + delivery)承 phase2 语义；如需「一次审批覆盖交付」可合并节点或引入审批 scope，留待后续。
- [ ] 产出内容由流程定义提供(框架先行)，真实 LLM/网络调研未接——与 3.1/3.2 一致。
