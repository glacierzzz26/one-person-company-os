## 三、实现要点

- **零代码**:新品发布复用 3.2 跨 Capability 引擎与 5.1/5.2 的 memory/decision 落库;示例 definition 存 examples/。
- **两次审批**:approval 门与 delivery(high risk,git commit)各触发一次,须分别 approve;reject 审批门 → `workflow ... aborted at step approval: ... rejected by human`。
- **交付与已跟踪文件约定**(承 3.3/4.3):`git commit -am` 只提交已跟踪文件变更;6 业务文件预置骨架(git init + commit),file-write 改写,delivery 提交。
- **权限最小化**:6 内容角色 read/write file;quality 额外 execute/git(交付);默认拒绝。
- **`workflow run` 需保持存活**:审批门处轮询等待人工,须后台运行 run、前台 approve(本次 smoke 用 Bash 后台 + 前台审批)。

## 四、冒烟记录

环境：全新 DB `/tmp/opos-p5-full.db` + company ACME,8 Capability 22 Agent,launch-file + quality-git 两策略,git 工作区 `/tmp/opos-p5-ws-launch`(init 预置 6 骨架文件,1 commit)。

1. `workflow add product-launch-2` → `workflow run`(后台):research→product→engineering→qa→marketing→sales 完成,approval 门暂停。
2. `approval approve`(门)→ delivery 开始 → 再次暂停(high risk)。
3. `approval approve`(delivery)→ `git commit -am "deliver product launch"` → **8/8 nodes completed**,commit `95e5018`,6 文件内容更新。
4. 任务归属核对:7 执行节点 agent/capability 各归其主。
5. reject 场景:`workflow run`(product-launch-reject)到门 → `approval reject` → `aborted at step approval ... rejected by human`,delivery 未创建。
6. 决策:两次 approve 各落 1 条 kind=approval decision(source=approval:<id>);reject 也落 1 条。
7. `os overview`:8 Capability(22 agents)+ 3 流程状态(completed=8 / completed=6 failed=1)+ decisions + memory 高亮。

## 五、已知问题 / 待办

- [ ] **`workflow run` 阻塞等待审批**:门节点处轮询,需后台运行 + 前台审批;无「断点续跑」——run 被杀后需新建 workflow 重跑(本次 smoke 用第二个 workflow 规避)。后续可加 run 幂等/断点恢复。
- [ ] **新文件交付需 git add**(承 3.3/4.3):当前靠预置已跟踪骨架规避。
- [ ] Business/工程 Agent 无真实外部系统(CRM/ERP/支付/LLM)接入(框架先行,0-5 一贯边界)。
- [ ] Metrics 仅声明不采集(Prometheus/Dashboard 独立排期)。
