## 一、定位与目标

现状里,要「多一个例行活 / 一种工作形态」,理解上总归要动 Go(新判读解析、新执行原语、新外部触点),
或至少人肉铺 JSON 步骤(workflow 定义)。用户要把它推到底:**加一条流水线 = 在页面上写一段意图 + 护栏,
落库即生效,不改代码**;而跑起来后,由**高智模型当运行时架构师**——对着意图 + 可用资源现场拆阶段、
订每阶段的输入/输出契约与分配,OS 逐阶段验收执行。

同时给所有「项目的事」一个**物理容器**:一个项目一个目录(code、knowledge 等类型化子目录都收在下面),
这个项目绑定的所有流水线(不管 bugfix / 开发 / 运维)只能在这个目录内工作——目录 = 委派信任面,
也是 Phase 8「claude 在 git workspace 自主干」从任务级升级到**项目级**的落点。

三个目标(验收时逐条可证):

1. **声明式流水线**:流水线 = 一段「意图 + 护栏」(结构化字段 + 自然语言描述 + 工具/凭据引用 + 风险),
   在 Web 控制台编写、落库即生效;**加一条新流水线不写代码**。
2. **高智运行时合成**:执行时 frontier 模型对「意图 + 该项目可用资源(子目录/凭据/端点档位)」现场合成
   **阶段计划**——拆几段、每段输入/输出契约、分给谁(委派 claude / 网关判读)、怎么验收;
   例行流水线用**模板化计划**(可重现、可跨天比较),高智自由合成只留给非例行。
3. **项目 = 目录容器**:一等实体「项目」= 一个目录容器(可含 code/、knowledge/ 等子目录 + 代码源绑定)
   + 绑定的流水线集合 + 项目级凭据/环境引用;**该项目所有流水线的 do 阶段只写该目录内**,
   OS 用既有 git 捕获 + 治理(审批/熔断/审计)兜底。

## 三、目标架构(方向;D7 落定后细化)

```
company(隔离/机密/通知/console,Phase 9 既有)──┬── project P(一等实体:目录容器 · 唯一委派信任面)
                                               │      P/code/       代码(开发 / bugfix 的 do 面)
                                               │      P/knowledge/  知识库(与 Memory 关系见开放点 6)
                                               │      P/<其他类型子目录…>
                                               └──   流水线集合(绑 P,只能在此目录内工作):bugfix · 开发 · 运维巡检 …
   每条流水线 = 声明式意图:[结构化字段(工具/凭据引用/risk/schedule)] + [自然语言描述]
       页面作者面(Phase 7.3 控制台扩展)→ 落库即生效,加流水线不改代码
                                  ▼ 认领 / 到点
   frontier 运行时合成(8.4 档位已就位):对 意图 + 该项目可用资源(子目录/凭据/端点档) → 阶段计划
     阶段 = { 目标 | 输入(前序产出) | 输出契约 | 分配(委派 claude / 网关判读) | 验收方式 }
       计划可审;高风险 / 碰生产 → 先给人 approve 再执行(复用 approval 门)
                                  ▼ OS 逐阶段驱动
     do 阶段    → 委派 claude 在项目目录内干(简报含子目录边界 + 约束)
     验收阶段   → 能机械验证(测试/构建/原始证据)→ OS 直接执行当验收;
                 无机械判据 → 网关模型判读;不信任 agent 自述(延续 8.2/8.4 原则)
     过契约才 advance;不过 → 返工 / 熔断 / 问人(沿用既有语义);全程审计记「计划 + 每阶段产出」
```

**治理口径(方向层定,与既有资产一致)**:文件边界 = 项目目录(委派唯一可写面);影响边界 = 凭据只读/风险门
(碰生产 = 只读优先 + 变更动作过另一个维度)。二者正交,分开写、分开管。新实体配置一律走 Web/DB,
**产品零 env(9.4 反向门控沿用)**。

## 四、方向决策(定稿;2026-09-07 定稿门确认后锁定,只读)

- **D1 项目 = 目录容器(一等实体)✅**:含 一个目录(唯一工作/委派面,类型化子目录 code/knowledge/…)+
  绑定的流水线集合 + 项目级凭据/环境引用。取舍:OS 收编「散在 task/repo/workflow 的 workspace 概念」
  到项目上,迁移成本换「信任边界一个文件夹、流水线不串目录」。
- **D2 流水线 = 声明式意图,落库即生效 ✅**:作者面 = Web 页面(结构化字段 + 自然语言描述 + 工具/护栏),
  新建/编辑不改代码。取舍:把「定义流水线」完整搬进数据 + UI;引擎在现 Workflow Engine 之上扩展
  (节点字段增 schedule/凭据引用/intent),不另起一套任务形态。
- **D3 运行时合成:例行模板化先行,合成放 10.4 ✅(定稿门)**——例行流水线**默认模板化计划**(固定检查项,
  模型只解释执行)保可重现、可跨天比较;高智 frontier 合成留给非例行(意图无模板时,10.4 接入,有例行模板垫底)。
- **D4 阶段验收分层 ✅**:能机械验证的(测试/构建/原始证据)由 **OS 直接执行当验收**,模型判读只用于
  无机械判据处;一切产出不信任 agent 自述(证据内嵌报告)。取舍:开发量换「模型批模型自证闭环」风险的解除。
- **D5 治理延续 ✅**:审批门/熔断/审计/账本/父子聚合逐字复用;8.4 档位 + 9.4 零 env 是合成/分层的**已就位硬前提**。
- **D6 首期锁三类形态 ✅(定稿门)**——bugfix / 开发 / 运维巡检,按项目参数化;等真出现第 4 种再泛化。
  取舍:不做「通用流水线工厂」大抽象,让通用从真实差异长出来(延续用户务实主义)。
- **D7 项目实体与 company/repo 的关系 → 案 A ✅(定稿门选定)**:**项目 = company 下新一等实体
  (repo 收敛为其 code 源绑定)**。company 保持 配置/机密/通知 隔离语义,项目 = 目录容器 + 流水线集合 +
  项目级凭据引用;「一人公司 = 单 company 下多项目」自洽;channel B 的 repo 变为 project 下一类绑定
  (issue→project/code 目录)。取舍:新表 + repo 语义微调(只增不改,迁移兼容),换来 company(配置)与
  project(干活目录)解耦,可多项目共享同一凭据/通知层。

## 五、边界 / 不做(候选)

- **不做 CI/CD**:用户明确暂时不做发布流水线/持续集成。
- **不放开「OS 直连任意外部系统」**:执行仍走委派 + 网关判读;新外部触点以 凭据最小化 + 只读优先 +
  主机 allowlist + 变更过人 为前置(承 8.3 委派边界),OS 不自研逐 call 外部编排。
- **不改 0-9 已冻结契约与语义**:回合/端点/审批/审计/API 字段逐字保留;迁移只增不改;产品零 env 不变。
- **不做通用 YAML IDE(首期)**:作者面 MVP = 模板化表单 + 描述框(开放点 9);YAML 编辑器/校验/dry-run 放实施后期。

## 六、开放设计点(方向层口径已定 ✅/实施层再解 ⭕;如实列出,不提前拍死)

1. **验证可信度(模型批模型)**:代码改对没 → 真正裁判是 `go test`/build 跑一遍;巡检 → 报告内嵌**原始证据**
   (命令输出/返回码),不收 claude 总结。D4 是口径,落地形态实施层定。
2. **凭据与注入(运维用例生死线)**:委派进程带生产凭据 + 读项目目录/连外网 → 仓库内污染 issue/注释可能诱导
   持凭据 agent 越界。方向口径:凭据按项目最小化、只读优先、主机 allowlist、任何变更动作过人。
3. **闭环到真实世界(交付手续)**:委派产出是 OS 目录里一坨 diff —— 谁 review、谁合回上游/开 PR;
   巡检发现 → 谁决定行动(通知→人工 / 自动拉起同项目 bugfix 的**链式触发**)。不做这层会出现「OS completed,
   真实世界纹丝不动」。
4. **预算 / 失控 / 重现**:多阶段 + 合成 + 委派烧钱 → 阶段预算 + 全局预算 + 中途取消 + 成本可见;
   非确定性计划 → 例行模板化(承 D3)。
5. **git 布局与提交语义**:项目容器内再放 code:布局 A(整项目目录 = 一个 git 仓库)与 布局 B(容器普通目录,
   code 独立仓库)两种自洽走法;多流水线共享一目录 → OS 每次运行捕获 diff 落本地 commit 保下次认领起点干净
   (承 8.3 预留)+ 同目录串行执行。
6. **knowledge/ 与 Memory 的关系 ✅(定稿门:文件为准 + Memory 索引)**:knowledge/ 目录 = 唯一事实源
   (委派上下文可读、可 diff/版本化);Memory DB 只做索引(路径 + 元数据 + FTS),摄入时写文件 + 同步索引,
   索引可从目录重建(文件即真相)。
7. **档位实况**:合成要真 frontier —— 若用户网关只配单模型,分层纪律在但能力不分;方向把 8.4 档位当硬前提,
   网关实际配多模型与否由用户环境决定(不影响本方向立项)。
8. **触发源全集与单机现实**:定时 / 手动 / GitHub issue / 巡检发现→拉起 fix 的链式触发;多项目定时巡检若单
   worker 串行,时间账要在 schedule 设计里算清。
9. **UI 复杂度与 MVP**:YAML 编辑器/校验/dry-run 是实打实功能 —— 放实施后期;首期只做模板化表单 + 描述框。

## 九、风险与取舍

- **高智合成质量绑定 frontier** → 拆错白跑:例行模板化 + 高风险计划先给人批(approval 门),不让模型拆完闷头干。
- **模型批模型 / 自述可信度** → D4 机械验证优先 + 原始证据内嵌;模型判读只兜无机械判据处。
- **凭据泄露 / 注入越界** → 凭据最小化 + 只读优先 + allowlist + 变更过人;8.3 边界 + 9 机密治理是前提。
- **工程规模扩张** → 通用工厂一次全做是大工程:MVP 锁三类形态 + 每子阶段独立验收(承 D6)。
