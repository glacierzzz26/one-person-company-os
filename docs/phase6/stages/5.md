## 一、目标与范围

- 目标(设计 §10 6.5)：研发部(engineering Capability)状态在运营视图可见——pending/熔断/待审批/子任务
  计数与明细 + 通道 B issue_sync 账本回放(处置分布/去重计数)；飞书通知落地——熔断告警**即时**、
  **9:00 昨日摘要**、待审批提醒。
- 范围：`internal/notify`(飞书机器人 webhook 双 sink：`https://` 真实推送 / `file://` 离线邮箱
  test-double)；service 注入 notifier 并在 `requestApproval`(熔断 / planner ask / 高险门唯一汇点)
  事件点即时推送；overview 新增 RD 聚合块；昨日摘要(service 组装 + server 单协程定时 + CLI flag)。
- 边界：**不改任何引擎语义、无新迁移、无 sqlc 改动(复用现有查询 Go 内过滤)、无新 go.mod 依赖**
  (出站 net/http + stdlib hmac/sha256;定时用单协程 tick,robfig/cron 暂不引入,符合设计「首版单协程 tick」)。
  事件点即时通知由 service 内 notifier 承担;server 只负责每日摘要与既有轮询。

## 三、实现要点

- **通知触发点 = 事件点即时发(用户确认)**：熔断告警 / planner ask / 高险审批门都汇到 `requestApproval`
  一个中心点,转 waiting_approval 即同步推送——保证熔断 ≤1 分钟触达(设计 §10 验收)。每日摘要/待审批
  recap 由 server 定时承担,不在事件点重复。
- **notifier 双形态 + fail-open**：`NewFromEnv` 读 `OS_FEISHU_WEBHOOK`;为空返回 nil(=禁用,调用方
  nil 安全)——不配 webhook 时引擎照常熔断转 waiting_approval,流程零变化(S6 回归断言)。`https://` →
  真实飞书自定义机器人文本消息(`{"msg_type":"text","content":{"text":…}}`,secret 时带 sign);
  `file:///abs/path` → 追加写入(离线邮箱 test-double,镜像 `OS_ISSUE_SOURCE=fixture` 的 fixture 思路)。
  `notifyApproval` best-effort:发送失败仅 `log.Printf`,绝不回传错误影响审批流。
- **飞书签名 = base64 不是 hex**：custom-bot signed mode 要求顶层 `timestamp`+`sign` 字段,
  sign = base64(HMAC-SHA256(key=secret, data=`timestamp+"\n"+secret`))。计划初稿曾写 hex,实现按官方
  规格修正并单测重算断言。
- **RD 任务集天然含子任务**：`buildRD` 用 company 全量 `ListTasks` + Go 内过滤(tool=engineering 或
  capability_id=engineering),拆解子任务继承父 capability → 自动落入部门视图,无需新查询。
  熔断判定双保险:`ConflictCount >= engFuseMax(3)` 或 waiting 原因前缀 `engineering fuse`
  (兼容无 pending approval 行的中断态)。账本 = `ListIssueSync` 按 disposition 计数(处置分布 +
  去重计数 = 总条数)。
- **摘要窗口 = 近 24h**：9:00 例行即「昨日 9:00 → 今日 9:00」,首日/任意时刻启动都可给出有意义内容;
  server 定时仅决定「几点发」,发哪 24h 由窗口语义统一,避免首日 9:00 前启动无内容。
- **nextDigestFire 宽限**：已过点 ≤2min 视作「刚到点」仍发当日(弥补启动/时钟抖动);超过则顺延次日,
  跨午夜由 `today.Add(24h)` 自然处理。单协程 tick 到点发一次,失败只记日志不退出。

## 四、冒烟记录

环境:全新 DB + engineering capability + `OS_ENGINE_MODE=scripted` + `OS_ISSUE_SOURCE=fixture`
(离线全确定性);通知用 `OS_FEISHU_WEBHOOK=file://<mailbox>`(每场景独立 DB + 独立 mailbox,防混)。

1. **S1 overview RD 块**：造 完成 1(direct_work issue 跑完)+ 熔断 1(`OS_SCRIPT_REVIEW=reject` 连驳 3 次
   → waiting_approval conflict=3)+ 待审批 1(risk=high 审批门)+ 父+子任务各 1 + 账本 3 处置
   (direct_work #101 / skip #102 / merge #103,三条 fixture 分次 sync)→ `os overview --company`：
   `status: completed=1 pending=3 waiting_approval=2`;`fused=1 | waiting_approval=1 | subtasks=1`;
   fused 行(flaky auth refactor,conflict=3,reason=engineering fuse)+ waiting 行(billing migration,
   conflict=0,reason=risk=high);`intake ledger(3 seen): direct_work=1 merge=1 skip=1`。✅
2. **S2 熔断即时告警**：`OS_FEISHU_WEBHOOK=file:///…/fm.txt` + `OS_SCRIPT_REVIEW=reject` run 一条
   engineering task → waiting_approval;mailbox 含 `【研发熔断】task <short>` + 任务/risk/原因 +
   「评审连续驳回达阈值,已转人工审批。」+ `处理: os approval list → os approval approve|reject|changes <id>`;audit 见 eng_fuse。✅
3. **S3 待审批即时(非熔断)**：`OS_SCRIPT_PLAN=ask:need-human-scope` run 顶层任务 → waiting_approval;
   mailbox 含 `【待审批】` 且**不含**「熔断」字样;reason=planner ask。✅
4. **S4 昨日摘要**：造 完成 1 / 熔断 1(留 waiting)/ high 审批 approve 1(→ 审批通过 1 + decision 落库 1)/
   intake direct_work 1 → `os server --digest 09:00 --digest-now --poll 1`(file:// mailbox)→
   `【OS 研发日报 …】` + `新建任务 4 | 完成 1 | 失败 0 | 熔断(当前待人工) 1` + `当前待审批: 1 起(含熔断 1)` +
   `昨日审批: 通过 1 / 驳回 0 / 打回 0 | 决策落库 1 条` + `研发 intake(近24h, 1 条 issue): direct_work=1` +
   单公司 `os overview --company <id>` 提示。PASS 4/4。✅
5. **S5 https 真实路径**：仅 notify 单测(httptest 断言 method/ctype/msg_type/content + 含 secret 的 sign
   重算 + resp code≠0 报错),不发外网。✅
6. **S6 回归/fail-open**：不配 `OS_FEISHU_WEBHOOK` run 熔断 → 任务照常 waiting_approval + pending
   approval 建立 + 无 mailbox 文件(notifier disabled);既有 6.2/6.4 语义由 `go test ./...` 全量回归。✅

`go build -o bin/os ./cmd/os` 通过;`go test ./...` 全绿(新增 notify/service/server digest 单测)。

结论：overview 研发部 pending/熔断/待审批/子任务可见 + 账本处置分布回放;熔断/待审批事件点即时告警,
9:00 定时摘要经 `os server --digest` 落地——设计 §10(6.5) 本地离线验收全部满足。真实飞书机器人推送
由用户按 §五 验收。
