## 一、目标与范围

- 目标(设计 §10 6.4)：planner 拆解——整包工程请求拆成 ≤8 条真实子任务(挂父请求)；
  超出 8 条 / 边界不清 → ask_human(走既有 approval,无 bypass 开关)；两路接活——
  **通道 A**(公司 workflow engineering 节点整包请求)+ **通道 B**(merge 批次 issue)都进 planner。
- 范围：查询 `ListTasksByParent`(无迁移,0009 已含 parent_task_id)；planner 模型调用分界
  (live 走 planner/pool 端点 JSON 契约 / scripted 走 `OS_SCRIPT_PLAN`)；Engineering Driver 认领序曲
  (direct→回合机 / split≤8→建子任务同步驱动聚合 / ask→人工审批)；Intake merge 处置物化 umbrella 入队。
- 边界：无新增迁移、无新增依赖；真实(Claude)planner 端点验收留用户(与 6.2/6.3 live 一致)。
  治理(risk=high 审批)语义不变：高险请求仍在预审门 ask 人工,approved 后按原样执行不再自动拆。

## 三、实现要点

- **planner 属于 Driver 序曲,不改 workflow 引擎**:通道 A workflow 的 engineering 节点创建出的
  就是「整包请求」任务;认领(runEngineering)时先过 planner——direct 落入回合机、split 同步驱动
  子任务后 `CompleteTask` 父任务(摘要「planner decomposed into N subtask(s)」)返回。workflow 引擎
  视角父任务就是普通节点任务(completed 即放行下一节点),顺序/中断/审批门语义零改动。
- **无 bypass 开关**:>8 / 缺子项 / 边界不清 → `requestApproval`(复用 risk/审批机)。approve 后任务重新入队,
  再认领时 `HasApprovedApproval>0` → planner 序曲直接放行(direct),请求按整包执行——人类用 approve
  表达了「整体照做」,拆解不重复问;reject/changes 走既有 fail 语义。scripted 的 `split:9`/`ask:` 即演示
  「模型想拆 >8」时系统拒绝自动拆。
- **拆解深度有界(设计 §10)**:仅 `parent_task_id IS NULL` 的顶层请求过 planner;子任务是执行单元,
  认领即走 6.2 回合机。防递归拆解失控,单次认领最多两层(父 + 子)。
- **续跑幂等**:父认领先查 `ListTasksByParent`;子任务已存在(上次拆解后租约中断/机器重启)→ 不重拆,
  直接驱动现存子任务聚合。子任务以 `MaxAttempts=2` 创建(planner 自动驱动,单次模型抖动不整包失败),
  驱动循环内置 requeue 让出,不热转。
- **merge 处置落地(6.3 待办收口)**:`IntakeIssues` 中 merge 与 direct_work 一样 create umbrella
  engineering task 入队(账本 disposition 仍记 merge、note 注明)。真实拆不拆由运行期 planner 判,
  triage 的 direct_work/merge 只反映入口直觉、不再各走一套。
- **子任务血缘**:继承父任务 company/workflow/capability/agent/risk/workspace/endpoints,title 来自
  planner 子项;父无 capability 时回退 engineering coding agent(同 intake 建任务解析)。audit:
  `eng_plan`(split 数量)/ `eng_plan_ask`(ask 理由)/ `eng_plan_done`(聚合摘要),actor=planner。
- **子任务审批等待**:driveChildTask 镜像 workflow 轮询语义;子任务熔断 → waiting_approval → 父序曲
  轮询等待(外部 `os approval` 仍可下达),approve 后子任务续跑完成、父才聚合。

## 四、冒烟记录

环境:全新 DB(ACME64)+ engineering capability(coding/qa agent)+ `OS_ENGINE_MODE=scripted` 全离线确定性。

1. **场景 A 通道 A 拆解**：`workflow add`(skip 输入 → engineering 节点,`tool: engineering`,描述为三模块 PRD)→
   `workflow run` + `OS_SCRIPT_PLAN=split:3` → **1/1 nodes completed**;父任务 completed(摘要
   「planner decomposed into 3 subtask(s)」)+ 3 子任务 completed 各挂 parent_task_id;每子任务 3 条
   execution(writer/test/review 回合机);audit 见 eng_plan/eng_plan_done。
2. **A2 引擎跨聚合节点续跑**：两节点 workflow(split 大活 → 收尾节点)→ **2/2 completed**;节点任务树 2 父 + 6 子全部 completed。
3. **场景 B 通道 B merge 拆解**：repo add + fixture 2 issue + `OS_SCRIPT_TRIAGE=merge` → `intake sync`
   建 2 umbrella task(账本 disposition=merge,task_id 关联,note=planned-batch);run #201 umbrella +
   `OS_SCRIPT_PLAN=split:2` → 父 completed + 2 子 completed。**通道 B issue 亦拆解** ✅
4. **场景 C ask_human(>8)**：create 顶层 engineering task + `OS_SCRIPT_PLAN=split:9` → run →
   **waiting_approval**(approval reason 引 >cap 8,无子任务);`approval approve` → decision 自动落库
   (审批 approved: …);重跑(仍 split:9)→ **completed,0 子任务,0 新增 pending approval**——
   approve 标记放行按原样执行,不重复问、无 bypass。
5. **场景 D direct 回归(6.2 语义)**：默认 `OS_SCRIPT_PLAN`(direct)→ run completed,0 子任务。
6. **场景 E 熔断回归(6.2 语义)**：`OS_SCRIPT_REVIEW=reject` → 3 次驳回 → conflict=3 → waiting_approval →
   approve → 续跑 humanOverride 放行 completed(round 3 conflict 0),planner 序曲未介入(0 子任务)。
7. **场景 F 续跑幂等**：父任务手动预置 1 子任务 → run 父(仍 split:3)→ 只驱动已有 1 子任务聚合完成,
   不重复拆(children=1)。
8. **场景 G live fail-closed**：无端点 + 非 scripted → run 报
   `plan: company …: no active model endpoint (add with 'os endpoint add', or OS_ENGINE_MODE=scripted…)`,
   任务 failed(phase=plan),0 子任务。

单测:`go test ./internal/service` 通过(TestParsePlan 10 子用例 + TestEngScriptedPlan 5 断言)。

结论：两路接活(通道 A workflow engineering 节点 / 通道 B merge batch)整包请求 → planner ≤8 拆解 →
子任务全部跑完聚合,>8 ask_human 无 bypass——设计 §10(6.4) 验收本地全部满足。真实 Claude planner 端点
(拆解质量)由用户按 §五 验收。

## 五、已知问题 / 待办

- [ ] **真实 planner 验收(用户)**：公司配 planner/pool 端点(`os endpoint add` + `OS_ENDPOINT_KEY`)后,
  把 6.2/6.3 待办的工程任务真正驱动:workflow engineering 节点 + 真实 Claude 拆解 ≤8、>8 ask_human,
  子任务带端点(或继承)走真实回合机。
- [ ] **高险请求不自动拆**:risk=high 的整包请求在预审门先 ask 人工,approved 后按原样执行(direct)——
  这是「人工已对整包拍板」的安全语义,若后续要「先拆再审」需加显式拆解配置。
- [ ] **子任务端点继承**:通道 A/B umbrella 若无 writer/reviewer 端点,live 子任务仍 fail-closed;
  待用户 endpoint 指派(或 6.5 运营视图辅助)。
- [ ] **并发认领**:父任务聚合期间若另一 worker 轮询到已 ready 子任务会抢先执行——单算子 OS 风险低,
  由 driver 轮询幂等兜底;多 worker 部署时需认领锁语义。
- [ ] **overview 归组**:拆解后 overview 的 workflow 任务计数把父子都计入同 workflow(可接受,备注);
  如需只看子任务层级归到父请求需加分组。
