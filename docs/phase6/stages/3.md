## 三、实现要点

- **issue_sync 表是 6.3 实现细化**(不在设计 §5.2 表清单,归档裁定)：通道 B 需要「同一条 issue 不重复建任务」的账本。`UNIQUE (repo_id, issue_number)` 原生去重 → webhook 优先 + 轮询兜底天然幂等;行内记 disposition/note/task_id,供 overview/回放(6.5 用)。
- **去重先于处置**:IntakeIssues 对每条 issue 先查账本,已存在 → 跳过(记 Already);再分诊 → 处置 → upsert 账本。triage 失败不落账本(下轮重试)。
- **webhook 实时优先 + 轮询兜底**:server 启动即同步一次、随后每 poll 间隔一次(设计 ≥5 分钟,默认 5;冒烟 `--poll 1` 只是验证轮询通道,与真实周期无关);webhook 命中同一账本不重复。
- **每 issue 一次分诊模型调用**(设计 §6.1):输出 `DISPOSITION: direct_work|ask|skip|merge(:note)` 容错解析;四处置均落账本,只有 direct_work 物化成 engineering task(入队即 ready)。ask 在真 GitHub 源(实现 PostComment 接口)下回帖,离线仅落 note;merge 记批注待 6.4 planner。
- **triage 端点**:live 取公司 role=planner 的活动端点,否则任一活动 pool;无端点 fail-closed 报错提示 `os endpoint add` 或 `OS_ENGINE_MODE=scripted`。engine.go 抽出 `modelCall(ctx, endpoint, prompt)` 供 6.2 各阶段与 intake 共用,去重解密/调 ClaudeCLI 逻辑。
- **intake 建任务的审计 actor**:`createTask` 新增 actor 参数,CLI 路径 human:cli,intake 路径 `intake`(诚实血缘,不伪装人)。task 行 tool=engineering、workspace 沿仓库登记、描述带 `source:` issue 链接;writer/reviewer 端点留空(planner/人工指派,6.4),直接 run 仍走 6.2 fail-closed。
- **服务化最小面**(设计 §8)：HTTP=chi;定时首版单协程 tick(不引 robfig/cron,后续可换);通知(飞书)归 6.5。
- **离线确定性冒烟**(§12 #1 保留):OS_ENGINE_MODE=scripted 时 triage 走 OS_SCRIPT_TRIAGE(`""/direct_work` 默认、`ask:<q>`、`skip:<reason>`、`merge:<note>`);issue 源 fixture 时无需真实 GitHub。

## 四、冒烟记录

环境:三份全新 DB(ACME63/ACME63B/ACME63C/ACME63D)+ fixture JSON 模拟 issue。

1. **场景 A 登记 + direct_work 入队**：`repo add`(URL github.com/acme63/opos-demo,workspace ws-demo)→ `intake sync` → 2 条 issue → 2 条 engineering task(pending/ready,`os task show` 见 Tool=engineering / Capability=engineering / Agent=coding / Workspace=ws-demo / 描述带 source 链接)。
2. **A2 去重幂等**：同一 fixture 二次 `intake sync` → 0 新增;issue_sync 账本 2 行(disposition=direct_work + task_id)。
3. **场景 B skip**：OS_SCRIPT_TRIAGE=skip:… → 0 任务;账本 disposition=skip、note=not-actionable-rewrite-all。
4. **场景 C server + webhook**：`os server --port 8791` → `/healthz` 200;POST issues.opened(#100)→ 200 + engineering task 落库(webhook 实时)。`--poll 5` 启动即同步 → fixture #42/#43 亦入队,总计 3 任务无重复(webhook 与轮询共享账本)。
5. **场景 D live fail-closed**：无端点 + 非 scripted → `intake sync` 报 `no active model endpoint (add with 'os endpoint add', or OS_ENGINE_MODE=scripted...)`,0 任务。

结论：本地可测机制全部符合设计 §10(6.3) 验收(仓库→issue→分诊→研发队列,webhook 实时优先);真实 GitHub 仓库/公网 webhook 由用户按 §五 验收。

## 五、已知问题 / 待办

- [ ] **planner 拆解 + 合并批次落地(6.4)**：本子阶段 merge 只落批注;通道 B issue 亦拆解、超 8 ask_human、通道 A(公司 workflow engineering 节点)接活。
- [ ] **issue_sync 是实现细化**:账本表不在 §5.2;回放/清账/重开事件(edited→re-triage)语义后续按需收口。
