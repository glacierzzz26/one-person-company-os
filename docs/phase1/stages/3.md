# Phase 1.3 — Workflow Engine 归档

> 阶段收口凭证。已冻结，只读。

## 一、目标与范围

- 目标：让 Workflow 从"仅存储 definition"变成"可执行编排"——解析有序节点，按序自动创建并推进各节点 Task，节点失败默认中断。
- 范围（设计文档 `docs/phase1/design/execution-kernel.md` 子阶段 1.3 + 第 8 节）：definition 解析、节点 → Task 生成（挂 `workflow_id`）、按序执行、失败中断、CLI（`os workflow run`）、按 role 解析 agent。
- 边界：节点间并行（Phase 1 顺序执行）、跨 Capability 编排（Phase 3）不做；Approval 触发（1.4）不做。

## 二、交付物

| 交付物 | 验证方式 | 结果 |
|---|---|---|
| `os workflow run <id>` 按序生成并执行节点 Task | smoke：3 节点 workflow → 3 task 全部 completed | ✅ |
| 节点失败默认中断，后续节点不创建 | smoke：节点 2 `exit 1` → abort，节点 3 未创建 | ✅ |
| 节点 `agent_role` → Agent 解析 | 节点 task 关联对应 role 的 agent（按公司查） | ✅ |
| 引擎运行落 Audit | `os audit list --entity-type workflow` 有 `run`（3/3 / aborted）记录 | ✅ |

## 三、实现要点

- **Definition 契约**：`workflow.definition`(JSON) 为有序节点数组，节点字段 `step / title / description / agent_role / risk / workspace`。`description` 即节点 Task 要执行的命令（Phase 1 语义，经 Tool 沙箱运行）。
- **执行流程**（`service.RunWorkflow`）：GetWorkflow → 解析 definition → 逐节点：按 `(company_id, agent_role)` 查第一个 Agent（新查询 `GetAgentByRole`，join capability）→ 创建 Task（挂 `workflow_id`、risk、独立 workspace）→ `ExecuteTask` 立即执行 → 检查终态：非 completed → audit 记录 aborted 并返回错误（中断，后续节点不创建）。
- **Workspace 兜底**：节点未给 `workspace` 时引擎 `os.MkdirTemp` 生成独立目录，保证每个节点 Task 有隔离工作区（对齐 1.2 契约）。
- **顺序性**：节点间严格按 definition 顺序串行（Phase 1 不做并行）。
- **审计增强**：`os audit list` 增加 DETAIL 列，workflow run 的摘要（`3/3 nodes completed` / `aborted at step X`）可直接可见、可验证。
- 引擎创建的 Task 走 1.2 的 Tool 沙箱执行路径，复用权限校验（默认拒绝）与 Execution 落库。

## 四、已知问题 / 待办

- [ ] 节点只支持"命令即 description"的 Phase 1 语义；Agent 智能体编排（选择 Tool/模型调用）属 Phase 2。
- [ ] 无并行、无重试策略（节点 task 用 max_attempts=1）、无可配置中断策略（"可配置"预留，1.3 固定为中断）。
- [ ] Approval 触发（risk=high OR policy 规则）与 `waiting_approval` 流转（1.4）。
- [ ] `workflow` 本身无独立状态/进度视图，靠节点 Task 状态体现（后续可加 WorkflowRun 实体）。
