# Phase 1.2 — Tool + Workspace + Docker Sandbox 归档

> 阶段收口凭证。已冻结，只读。

## 一、目标与范围

- 目标：把执行环境从"本机 shell"升级为"可插拔 Tool + 独立 Workspace + Docker Sandbox"，并补上 Tool 调用前的权限校验（默认拒绝 + Audit deny）。
- 范围（设计文档 `docs/phase1/design/execution-kernel.md` 子阶段 1.2）：Tool 接口 + Registry（可热插拔）、首个 Tool = Shell、Docker Sandbox 容器内执行、Task 独立 Workspace、Tool 调用前权限校验（CheckPermission，未授权拒绝 + Audit）、CLI（`os tool list`）。
- 边界：Workflow Engine（1.3）、Approval 流程与 risk 策略判定（1.4）不做；权限校验只做"role 是否被授予 execute/shell"的布尔判定，risk=high 触发审批留待 1.4。

## 二、交付物

| 交付物 | 验证方式 | 结果 |
|---|---|---|
| Tool 接口 + Registry（可热插拔） | `internal/tool/`，Shell 注册为 "shell"；`os tool list` 可见 | ✅ |
| Docker Sandbox 容器内执行 | 授权 task 在容器内跑通，返回真实 stdout | ✅ |
| Task 独立 Workspace 挂载 | 容器内写 `marker.txt` → 宿主机 workspace 可见内容 | ✅ |
| 权限校验（默认拒绝） | 未授权 role 的 task → failed + `unauthorized`，命令未执行 | ✅ |
| Audit deny 记录 | `os audit list --entity-type tool` 有 deny 行 | ✅ |

## 三、实现要点

- **Tool 取代 Runtime**：`internal/runtime/`（1.1 的本机 ShellRuntime）整体删除，由 `internal/tool/` 接管执行能力。`tool.Tool` 接口含 Name / Description / Permission（Action+Resource）/ Risk / InputSchema / OutputSchema / Execute——对应方向基线 4.8 的 Tool 六要素。
- **Registry 按名字取**：`Register/Get/List` 与 1.1 同模式；新增/替换 Tool = 实现接口 + `init` 注册，执行引擎（service/execution.go）无感。首个 Tool = ShellTool。
- **Docker Sandbox 语义**：`docker run --rm --network none --cpus 1 --memory 256m -v <workspace>:/workspace -w /workspace busybox sh -c <task.Description>`。无网络、受限资源，Workspace 是 Task 与外界的唯一文件交换点。
- **Task 独立 Workspace**：task 创建时 `--workspace` 指定目录（缺省空则 ShellTool 报错，保证显式隔离）；容器内 `/workspace` 读写即宿主机 workspace 目录。
- **权限校验（Phase 1.2 布尔版）**：`service.runClaimed` 先取 Tool → `authorizeTool`：无 Agent → 拒绝；有 Agent 则取其 Role 为 subject，`CheckPermission(subject, action, resource)`（join enabled allow policy）> 0 才放行；否则 Audit `tool/<name> deny` + FailTask（last_error 含 unauthorized）。未授权命令**不会**进入容器。
- **默认拒绝**：没有匹配的 allow policy 即拒绝，不依赖 deny policy。
