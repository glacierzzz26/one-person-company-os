# One-Person Company OS — 使用说明

> 面向「一个人运营公司」的操作手册:构建、配置、命令、工作流定义与常见坑。
> 概念背景见 [项目详解](项目详解.md);阶段进度见 [进度总表](进度总表.md)。

---

## 一、这是什么

One-Person Company OS 是一个**由一个人负责最终决策、AI Agent 承担大量执行**的公司操作系统,单二进制 Go 程序 + SQLite(纯 Go,无 CGO)。

一条典型链路:

```
Human 定义方向 → OS 调度 Capability → Agent 执行 Task → Workflow 编排流程
→ Policy 限制边界 → 审批门把关 → Audit + Memory + Decision 沉淀公司资产
```

核心分层(方向基线 v1.1):

| 维度 | 结构 | 说明 |
|---|---|---|
| 组织 / 角色 | `Company → Capability → Agent` | Capability 是能力域(engineering/research/product/marketing/sales/operations/finance/customer),Agent 是其中的执行角色 |
| 流程 / 方法 | `Workflow → Task → Execution → Runtime → Tool` | Workflow 按序驱动 Task,Task 由 Worker 领取执行,Execution 是每次执行记录 |
| 治理链 | `Policy → Permission → Approval → Audit → Decision` | 系统强制实施,Agent 无法绕过 |

## 二、构建与启动

```bash
# 构建
go build -o bin/os ./cmd/os

# 配置(config/os.yaml):数据库路径 + Model Provider 声明
#   db_path: ./os.db
#   providers: 仅声明,Phase 2 为 stub,不真实调用 LLM
cat config/os.yaml

# 初始化数据库(打开即自动应用迁移,无需手动建表)
./bin/os init

# 全局参数
./bin/os --db /path/to/os.db <cmd>   # 覆盖 db_path(--config 指定其他配置文件)
```

- 数据库是单个 SQLite 文件,迁移(001-0006)在首次打开时自动应用。
- 所有命令都读同一个全局 DB;换 DB 用 `--db`。

## 三、快速上手(约 5 分钟)

```bash
# 1. 建公司(create/add 会打印完整 UUID,用 grep 抓进变量)
CID=$(./bin/os company create --name "ACME" --vision "做一人公司 OS" | grep -oP 'id: \K[0-9a-f-]{36}')
./bin/os company list

# 2. 建 Capability 与 Agent
CAP=$(./bin/os capability add --company $CID --code engineering --name "工程" | grep -oP 'id: \K[0-9a-f-]{36}')
AID=$(./bin/os agent add --capability $CAP --name "编码" --role coding | grep -oP 'id: \K[0-9a-f-]{36}')

# 3. 先授权(默认拒绝):coding 角色获得 execute/shell
POL=$(./bin/os policy add --company $CID --name "eng-exec" --kind allow --statement "coding 可执行 shell" | grep -oP 'id: \K[0-9a-f-]{36}')
./bin/os permission add --policy $POL --subject coding --action execute --resource shell

# 4. 建任务并执行(挂 Agent + workspace;shell 工具需要 workspace)
mkdir -p /tmp/ws
TID=$(./bin/os task create --company $CID --title "打声招呼" \
  --agent $AID --workspace /tmp/ws \
  --description 'echo hello from one-person-company' | grep -oP 'id: \K[0-9a-f-]{36}')
./bin/os task run $TID
./bin/os task show $TID   # Status: completed,Result 打印输出

# 5. 看看全公司状态
./bin/os overview --company $CID
```

> ⚠️ 外键/执行参数(`--capability/--agent/--policy` 等)需要**完整 UUID**,列表里显示的是短 ID。完整 UUID 从 create/add 的 `id: …` 输出抓。

## 四、命令参考

命令树(全部命令):

```
os

├── company    create | list | show
├── capability add  | list
├── agent      add  | list
├── policy     add  | list
├── permission add  | list
├── workflow   add  | list | run
├── task       create | list | show | run
├── queue      work
├── execution  list | show
├── tool       list
├── approval   list | show | approve | reject | changes
├── audit      list
├── provider   list
├── memory     add | list | search
├── decision   add | list | show
└── overview
```

### 4.1 公司 / 组织(`company`, `capability`, `agent`)

| 命令 | 用途 | 关键参数 |
|---|---|---|
| `company create` | 建公司 | `--name`(必填)`--vision` |
| `company list` / `show <id>` | 查公司 | — |
| `capability add` | 加能力域 | `--company --code --name`(必填)`--description` |
| `capability list` | 查能力域 | `--company`(必填) |
| `agent add` | 加 Agent 角色 | `--capability --name --role`(必填)`--model` |
| `agent list` | 查 Agent | `--capability`(必填) |

示例:

```bash
./bin/os capability add --company $CID --code research --name "研究" --description "市场/竞品研究"
./bin/os agent add --capability $CAP --name "市场研究员" --role market --model mock-1
```

### 4.2 任务(`task`)与执行(`execution`, `queue`, `tool`)

`task create` 是核心入口,`--description` 按所选工具解析为实际命令:

| 工具 | `--tool` | description 格式 | 示例 |
|---|---|---|---|
| shell | `shell` | 直接 shell 命令 | `'echo hi'` |
| git | `git` | git 子命令(本地白名单) | `git status`、`git commit -am "msg"` |
| 文件读取 | `file-read` | `read <path>` | `read research.md` |
| 文件写入 | `file-write` | `write <path>\n<内容>` | `write research.md\n# 标题\n内容` |
| AI 修复(mock) | `aifix` | 问题描述 | `修复空指针` |

```bash
./bin/os task create --company $CID --title "写研发方案" \
  --tool file-write --workspace /tmp/ws \
  --description 'write research.md
# 方案
MVP 先行' \
  --capability $CAP --agent $AID --risk low
./bin/os task list --company $CID --status pending
./bin/os task run <full-id>              # 单任务执行(claim + execute)
./bin/os queue work --worker w1 --limit 5  # 队列 worker,消费 READY 任务
./bin/os execution list --task <id>      # 每次执行的记录
./bin/os tool list                       # 已注册工具及权限
```

> ⚠️ shell 里写 `write x\n内容` 时,`\n` 是字面反斜杠。**用单引号包整段**才会得到换行。
> task description 里的换行即文件内容换行。

### 4.3 工作流(`workflow`)

```bash
./bin/os workflow add --company $CID --name "产品开发" \
  --description "8 阶段研发流程" --definition "$(cat def.json)"
./bin/os workflow list --company $CID
./bin/os workflow run <id> --worker w1    # 按序创建并执行节点 Task
```

- `run` 阻塞执行:逐节点创建 Task → 驱动到 completed;任一节点 failed → **中断**(abort)。
- 遇到审批门(waiting_approval)会**暂停等待人工**;`run` 必须保持存活(后台运行),approve 后自动续跑。
- 返回摘要如 `8/8 nodes completed`。

### 4.4 审批(`approval`)与审计(`audit`)

触发条件:**`risk=high` 的任务** 或 **approval 类 policy**。

```bash
./bin/os approval list --status pending   # 看谁在等你
./bin/os approval approve <id> --note "OK"    # 放行:任务重新入队执行
./bin/os approval reject  <id> --note "改"    # 拒绝:任务 failed
./bin/os approval changes <id> --note "补充"  # 打回:任务 failed 带说明
./bin/os approval show <id>
./bin/os audit list --entity-type task     # 追加式审计,不可改删
```

> approve/reject 后,审批结果会**自动落一条 decision**(kind=approval,source=approval:<id>),治理链闭环。

### 4.5 知识沉淀(`memory`)与决策(`decision`)

```bash
# Memory:公司知识,支持全文检索
./bin/os memory add --company $CID --type lesson --title "发布教训" \
  --content "审批门要前置,不要等交付才审" --tags "launch approval" --source "workflow:<wf-id>"
./bin/os memory list --company $CID --type lesson
./bin/os memory search --company $CID --q "审批"   # FTS5:≥3 字(中英文都支持),<3 字回退 LIKE

# Decision:公司决策记录(人工 + 审批自动落库)
./bin/os decision add --company $CID --kind strategy --title "Q3 主打国内市场" --body "…"
./bin/os decision list --company $CID --kind goal
./bin/os decision show <id>
```

### 4.6 全景视图(`overview`)与模型提供方(`provider`)

```bash
./bin/os overview --company $CID
# 7 个区块:Company / Capabilities×Agent 数 / Workflows 任务状态计数
#        / Pending Approvals(需要你决策)/ Recent Decisions / Recent Tasks / Memory Highlights

./bin/os provider list   # config 中声明的 Provider(stub)
```

## 五、工作流定义(JSON)

`os workflow add --definition` 接受一个**有序节点数组**。每个节点字段:

| 字段 | 必填 | 说明 |
|---|---|---|
| `step` | 是 | 节点标识(日志/进度显示) |
| `title` | 是 | 节点标题(生成 Task 标题) |
| `description` | 是 | 传给工具的指令(同 task create --description) |
| `tool` | 是 | `shell` / `git` / `file-read` / `file-write` / `aifix` |
| `agent_role` | 是 | 执行角色;**留空 = 审批门** |
| `capability` | 否 | Capability code;非空 → 按 (capability, role) 解析 Agent;空 → 公司级 role 回退 |
| `risk` | 否 | 默认 `medium`;`high` 触发审批 |
| `workspace` | 否 | 工作区目录;缺省自动建临时目录 |
| `skip` | 否 | `true` = 输入声明节点,不执行(只留审计) |

规则:
- **审批门**:`agent_role` 为空的节点 → Task 进入 `waiting_approval`,人工 approve 后直接放行(门节点无实际执行)。
- **跨 Capability**:节点声明 `capability` → 在对应 Capability 里按 role 找 Agent,Task 归属该 Capability。
- **风险触发**:`risk: high` 的节点(如 git commit 交付)无论角色都会卡审批。

一个最小示例:

```json
[
  {"step": "research",  "title": "市场研究", "tool": "file-write",
   "capability": "research", "agent_role": "market",
   "description": "write research.md\n# 研究\n……", "workspace": "/abs/path/ws"},
  {"step": "approval", "title": "审批门", "tool": "shell", "agent_role": "",
   "risk": "high", "workspace": "/abs/path/ws"},
  {"step": "delivery", "title": "交付", "tool": "git",
   "capability": "operations", "agent_role": "quality",
   "description": "git commit -am \"deliver\"", "risk": "high", "workspace": "/abs/path/ws"}
]
```

完整参考:新品发布 9 节点定义见 `docs/phase5/examples/product-launch-workflow.json`(跨 research/product/engineering/marketing/sales/operations 六大家族,含 skip 输入节点 + 两次审批门)。

## 六、权限与治理

**模型**:Policy(策略)→ Permission(权限,挂在策略下)。执行前校验,默认拒绝。

```bash
./bin/os policy add --company $CID --name "write-file" --kind allow \
  --statement "内容角色可写 workspace 文件"
./bin/os permission add --policy <policy-id> --subject coding --action write --resource file
```

| Tool | 需要的 Permission |
|---|---|
| `file-read` | `read/file` |
| `file-write` | `write/file` |
| `shell` | `execute/shell` |
| `git` | `execute/git` |
| `aifix` | `execute/aifix` |

- `subject` = Agent 的 role 字符串(如 `coding`/`market`/`quality`)。
- 无对应权限 → 任务 failed,错误含 `permission denied`。

## 七、交付约定(git)

git 工具只放行**本地操作**(init/status/add/commit/diff/log/…),网络操作(clone/pull/push/fetch)**不支持**。

关键坑:`git commit -am` **只提交已跟踪文件**。新文件不会被提交。约定做法:

```bash
# 1. 工作区先 git init 并预置业务文件骨架(占位提交一次)
cd /path/to/ws && git init -q && git add . && git commit -qm "skeleton"
# 2. 工作流里 file-write 改写这些已跟踪文件
# 3. delivery 节点 git commit -am "deliver ..." 才会带上改动
```

## 八、常见坑速查

| 现象 | 原因 / 对策 |
|---|---|
| 外键错误 `FK constraint (787)` | 传了短 ID;`--capability/--agent/--policy` 用完整 UUID |
| 任务 failed `workspace path is empty` | shell/git/file 工具都要求 workspace;`task create --workspace <dir>` |
| 文件内容 0 字节 / 文件名带 `\n` | shell 里 `\n` 是字面量;description 用单引号整段包裹 |
| `workflow run` 卡在审批门不结束 | 设计如此(run 需保持存活);**后台运行 run,前台 approve** |
| run 被杀后重跑报任务已存在 | 无断点续跑;新建一个 workflow 实例重跑 |
| `memory search 反馈` 无结果 | FTS5 trigram 需要 ≥3 字;2 字查询自动回退 LIKE,含义放宽 |
| 交付 commit 没带上新文件 | `git commit -am` 只提交已跟踪文件;先 git init + 预置骨架 |
| 任务 failed `permission denied` | 未授权;`policy add` + `permission add` 给角色授权 |
| 审批没触发 | 只有 `risk=high` 或 approval policy 才触发;节点 risk 默认 medium |
