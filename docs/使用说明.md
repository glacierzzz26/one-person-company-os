# One-Person Company OS — 使用说明

> 面向「一个人运营公司」的操作手册:构建、配置、命令、工作流定义与常见坑。
> 概念背景见 [项目详解](项目详解.md);阶段进度见 [进度总表](进度总表.md)。

---

## 一、这是什么

One-Person Company OS 是一个**由一个人负责最终决策、AI Agent 承担大量执行**的公司操作系统,单二进制 Go 程序 + SQLite(纯 Go,无 CGO)。

一条典型链路:

```
Human 定义方向 → OS 调度 Capability → Agent 执行 Task → Workflow 编排流程
→ Policy 限制边界 → 审批门把关 → Audit + Memory + Decision 沉淀公司资产
```

核心分层(方向基线 v1.1):

| 维度 | 结构 | 说明 |
|---|---|---|
| 组织 / 角色 | `Company → Capability → Agent` | Capability 是能力域(engineering/research/product/marketing/sales/operations/finance/customer),Agent 是其中的执行角色 |
| 流程 / 方法 | `Workflow → Task → Execution → Runtime → Tool` | Workflow 按序驱动 Task,Task 由 Worker 领取执行,Execution 是每次执行记录 |
| 治理链 | `Policy → Permission → Approval → Audit → Decision` | 系统强制实施,Agent 无法绕过 |

## 二、构建与启动

```bash
# 构建
go build -o bin/os ./cmd/os

# 配置(config/os.yaml):数据库路径 + Model Provider 声明
#   db_path: ./os.db
#   providers: 提供方声明;真实模型走 os endpoint(见 §4.7),离线冒烟 OS_ENGINE_MODE=scripted
cat config/os.yaml

# 初始化数据库(打开即自动应用迁移,无需手动建表)
./bin/os init

# 全局参数
./bin/os --db /path/to/os.db <cmd>   # 覆盖 db_path(--config 指定其他配置文件)
```

- 数据库是单个 SQLite 文件,迁移(001-0009)在首次打开时自动应用。
- 所有命令都读同一个全局 DB;换 DB 用 `--db`。

## 三、快速上手(约 5 分钟)

```bash
# 1. 建公司(create/add 会打印完整 UUID,用 grep 抓进变量)
CID=$(./bin/os company create --name "ACME" --vision "做一人公司 OS" | grep -oP 'id: \K[0-9a-f-]{36}')
./bin/os company list

# 2. 建 Capability 与 Agent
CAP=$(./bin/os capability add --company $CID --code engineering --name "工程" | grep -oP 'id: \K[0-9a-f-]{36}')
AID=$(./bin/os agent add --capability $CAP --name "编码" --role coding | grep -oP 'id: \K[0-9a-f-]{36}')

# 3. 先授权(默认拒绝):coding 角色获得 execute/shell
POL=$(./bin/os policy add --company $CID --name "eng-exec" --kind allow --statement "coding 可执行 shell" | grep -oP 'id: \K[0-9a-f-]{36}')
./bin/os permission add --policy $POL --subject coding --action execute --resource shell

# 4. 建任务并执行(挂 Agent + workspace;shell 工具需要 workspace)
mkdir -p /tmp/ws
TID=$(./bin/os task create --company $CID --title "打声招呼" \
  --agent $AID --workspace /tmp/ws \
  --description 'echo hello from one-person-company' | grep -oP 'id: \K[0-9a-f-]{36}')
./bin/os task run $TID
./bin/os task show $TID   # Status: completed,Result 打印输出

# 5. 看看全公司状态
./bin/os overview --company $CID
```

> ⚠️ 外键/执行参数(`--capability/--agent/--policy` 等)需要**完整 UUID**,列表里显示的是短 ID。完整 UUID 从 create/add 的 `id: …` 输出抓。

### 4.1 公司 / 组织(`company`, `capability`, `agent`)

| 命令 | 用途 | 关键参数 |
|---|---|---|
| `company create` | 建公司 | `--name`(必填)`--vision` |
| `company list` / `show <id>` | 查公司 | — |
| `capability add` | 加能力域 | `--company --code --name`(必填)`--description` |
| `capability list` | 查能力域 | `--company`(必填) |
| `agent add` | 加 Agent 角色 | `--capability --name --role`(必填)`--model` |
| `agent list` | 查 Agent | `--capability`(必填) |

示例:

```bash
./bin/os capability add --company $CID --code research --name "研究" --description "市场/竞品研究"
./bin/os agent add --capability $CAP --name "市场研究员" --role market --model mock-1
```

### 4.2 任务(`task`)与执行(`execution`, `queue`, `tool`)

`task create` 是核心入口,`--description` 按所选工具解析为实际命令:

| 工具 | `--tool` | description 格式 | 示例 |
|---|---|---|---|
| shell | `shell` | 直接 shell 命令 | `'echo hi'` |
| git | `git` | git 子命令(本地白名单) | `git status`、`git commit -am "msg"` |
| 文件读取 | `file-read` | `read <path>` | `read research.md` |
| 文件写入 | `file-write` | `write <path>\n<内容>` | `write research.md\n# 标题\n内容` |
| AI 修复(mock) | `aifix` | 问题描述 | `修复空指针` |
| 研发(工程请求) | `engineering` | 整包研发请求,Engineering Driver 写→测→审回合机驱动(熔断/拆解见 §4.7) | `修登录 bug:会话提前过期` |

```bash
./bin/os task create --company $CID --title "写研发方案" \
  --tool file-write --workspace /tmp/ws \
  --description 'write research.md
# 方案
MVP 先行' \
  --capability $CAP --agent $AID --risk low
./bin/os task list --company $CID --status pending
./bin/os task run <full-id>              # 单任务执行(claim + execute)
./bin/os queue work --worker w1 --limit 5  # 队列 worker,消费 READY 任务
./bin/os execution list --task <id>      # 每次执行的记录
./bin/os tool list                       # 已注册工具及权限
```

> ⚠️ shell 里写 `write x\n内容` 时,`\n` 是字面反斜杠。**用单引号包整段**才会得到换行。
> task description 里的换行即文件内容换行。

### 4.3 工作流(`workflow`)

```bash
./bin/os workflow add --company $CID --name "产品开发" \
  --description "8 阶段研发流程" --definition "$(cat def.json)"
./bin/os workflow list --company $CID
./bin/os workflow run <id> --worker w1    # 按序创建并执行节点 Task
```

- `run` 阻塞执行:逐节点创建 Task → 驱动到 completed;任一节点 failed → **中断**(abort)。
- 遇到审批门(waiting_approval)会**暂停等待人工**;`run` 必须保持存活(后台运行),approve 后自动续跑。
- 返回摘要如 `8/8 nodes completed`。

### 4.4 审批(`approval`)与审计(`audit`)

触发条件:**`risk=high` 的任务** 或 **approval 类 policy**。

```bash
./bin/os approval list --status pending   # 看谁在等你
./bin/os approval approve <id> --note "OK"    # 放行:任务重新入队执行
./bin/os approval reject  <id> --note "改"    # 拒绝:任务 failed
./bin/os approval changes <id> --note "补充"  # 打回:任务 failed 带说明
./bin/os approval show <id>
./bin/os audit list --entity-type task     # 追加式审计,不可改删
```

> approve/reject 后,审批结果会**自动落一条 decision**(kind=approval,source=approval:<id>),治理链闭环。

### 4.5 知识沉淀(`memory`)与决策(`decision`)

```bash
# Memory:公司知识,支持全文检索
./bin/os memory add --company $CID --type lesson --title "发布教训" \
  --content "审批门要前置,不要等交付才审" --tags "launch approval" --source "workflow:<wf-id>"
./bin/os memory list --company $CID --type lesson
./bin/os memory search --company $CID --q "审批"   # FTS5:≥3 字(中英文都支持),<3 字回退 LIKE

# Decision:公司决策记录(人工 + 审批自动落库)
./bin/os decision add --company $CID --kind strategy --title "Q3 主打国内市场" --body "…"
./bin/os decision list --company $CID --kind goal
./bin/os decision show <id>
```

### 4.6 全景视图(`overview`)与模型提供方(`provider`)

### 4.7 研发部执行(Phase 6:`endpoint` / `engineering` / `repo` / `intake` / `server` / 飞书通知)

研发执行闭环:模型端点池 → 工程任务(回合机 写→测→审)→ 熔断/审批门 → 通道 B GitHub issue → 运营视图 + 飞书通知。

```bash
# 1. 模型端点池(6.1):真实调用配 os endpoint;离线冒烟 OS_ENGINE_MODE=scripted(全模型走固定脚本)
./bin/os endpoint add --company $CID --provider claude --name "claude" --model "claude-opus-5"   # key/url 按需
./bin/os endpoint list --company $CID
./bin/os endpoint select --company $CID --id <endpoint-id>   # 设为公司默认
./bin/os endpoint models --provider anthropic                # 查厂商模型(需网络)

# 2. 工程任务 --tool engineering → Engineering Driver 回合机(写→测→审;测试失败免费返工)
TID=$(./bin/os task create --company $CID --capability $CAP --tool engineering \
  --title "修登录 bug" --description "会话提前过期,需刷新续期" | grep -oP 'id: \K[0-9a-f-]{36}')
./bin/os queue work --limit 1          # 认领执行;评审连驳 3 次 → 熔断 waiting_approval
./bin/os approval list                 # 熔断/高险门/planner ask 都汇到审批,人工 approve|reject|changes

# 3. 通道 B:GitHub issue 自动进来(真实拉取配 OS_GITHUB_TOKEN)
./bin/os repo add --company $CID --name repo-x \
  --repo-url https://github.com/acme/repo-x --workspace /path/to/ws
./bin/os intake sync --company $CID     # 拉 open issue → 分诊(direct_work/merge/skip/ask)→ 建 task/记账本

# 4. 常驻服务:webhook + GitHub 轮询 + 每日摘要(本地时区 HH:MM 单协程到点发)
./bin/os server --port 8787 --poll 5 --digest 09:00     # --digest-now 启动即发一次(验证用)
./bin/os server --queue-work --queue-interval 10        # (7.2)server 自驱认领执行队列,免手动 os queue work
#    飞书通知:熔断/待审批事件点即时告警 + 9:00 昨日摘要,经同一 OS_FEISHU_WEBHOOK 机器人 webhook;
#    未配 = 通知禁用(引擎流程照常);离线可设 file:///tmp/mailbox.txt 当邮箱验内容。
```

- **离线确定性(冒烟/CI)**:`OS_ENGINE_MODE=scripted` + `OS_SCRIPT_TEST/REVIEW/PLAN/TRIAGE` 固定脚本,
  `OS_ISSUE_SOURCE=fixture` + `OS_FIXTURE_ISSUES=<json>` 用本地 issue 源——不发任何外网。
- **熔断语义**:评审连续驳回达阈值(conflict≥3)→ 转 `waiting_approval` + 飞书【研发熔断】即时告警;
  approve → conflict 归零、round 推进续跑,decision 自动落库。
- **拆解**:通道 A(workflow 的 `tool: engineering` 节点)与通道 B(merge 批次 umbrella)整包请求,
  运行期由 planner 拆成 ≤8 条真实子任务同步驱动聚合;>8 / 边界不清 → ask_human 审批,无 bypass。
- **账本**:每 issue 处置(直接做/跳过/合并)落 `issue_sync`,webhook 与轮询共用(天然去重);
  `os overview` 的 `== RD: Engineering ==` 块 + 每日摘要里可见处置分布。

### 4.8 运营控制台数据通道 `/api/v1`(Phase 7.1,7.2 补队列自驱)

CLI 之外的第二入口:`os server` 同端口暴露 `/api/v1` JSON API,给**SPA(7.2 设计定稿,见
`docs/phase7/design/console-ui.md`)/手机/脚本**读全景(overview 含 RD 块)并做核心人工决策
(审批/建任务/记决策/沉淀记忆/配端点仓库/触发 intake)。与 CLI 走**同一 service 面**,零语义差别;
完整端点契约见 `docs/phase7/design/web-console.md` §五。7.2 起,经 API 的写操作审计 actor =
`human:console`(CLI 记 `human:cli`);建的任务可被 server 自动消费。

```bash
./bin/os server --port 8787
#   /api/v1 认证:设 OS_API_TOKEN=<token> 启动 → 请求带 `Authorization: Bearer <token>`(constant-time);
#   未设 = 开放(仅限本地回环/可信网)。webhook 与 /healthz 不受影响。
#   队列自驱(7.2):加 --queue-work 后 server 每 --queue-interval 秒(默认 10)认领排空 pending/ready 任务,
#   审计 runtime:server;不带则仍用终端 `os queue work` 手动消费。

# 信封:{ok,data} / {ok:false,error:{code,message}};时间=int64 unix 秒;ID=完整 UUID;字段 snake_case;
#   可空字段(如 task.capability_id)返回 null。404 not_found(查无)/400 bad_request(缺必填)。
curl -s localhost:8787/healthz
curl -s localhost:8787/api/v1/companies
curl -s localhost:8787/api/v1/companies/$CID/overview          # 旗舰读:含 rd 研发部块(熔断/待审批/子任务/账本)
curl -s localhost:8787/api/v1/approvals?status=pending
curl -s -X POST localhost:8787/api/v1/approvals/$AP/decision \
  -H 'Content-Type: application/json' -d '{"decision":"approve","note":"OK 放行"}'
curl -s -X POST localhost:8787/api/v1/tasks \
  -H 'Content-Type: application/json' \
  -d "{\"company_id\":\"$CID\",\"title\":\"修登录 bug\",\"tool_name\":\"engineering\",\"risk\":\"medium\"}"
curl -s "localhost:8787/api/v1/companies/$CID/memories/search?q=审批门"      # 全公司记忆全文检索
curl -s -X POST localhost:8787/api/v1/companies/$CID/intake/sync             # 触发一次通道 B
#   Bearer 示例:curl -s -H "Authorization: Bearer $OS_API_TOKEN" …
```

- **读**:companies/overview/capabilities/agents/workflows/tasks+executions/approvals/decisions/memories+search/
  audit/endpoints+models/repos。
- **写**:建 company/task/decision/memory、配 endpoint(select/models)/repo、审批 decision、触发 intake sync。
- **不暴露(归 CLI/后台)**:`task run` / `queue work` / `workflow run`(长时阻塞),契约标 ❌;
  7.2 起队列消费可不手动 —— `os server --queue-work`(每间隔自驱认领,worker=server)。
- **actor 血缘(7.2)**:上述写端点经控制台/脚本调用时审计记 `human:console`;CLI 记 `human:cli`,
  intake/webhook 记 `intake:*` / `server:*`,执行记 `runtime:<worker>` —— 审计视图的 actor 即来源。
- 创建 task/decision/memory 的 actor 沿用 `human:cli`;7.1 无分页/CORS/RBAC。

### 4.9 Web 控制台(Phase 7.3:React + TS + AntD SPA)

`os server` 根路径直接托管浏览器控制台(8 视图),与 `/api/v1` **同一端口同一二进制**,零部署依赖。

```bash
# 构建嵌入 SPA(仓库根;make ui 自带 npm ci+build,首次需联网拉依赖):产 web/dist → cp 进 internal/console/ui(go:embed)
make ui            # 等价:cd web && npm ci && npm run build;rm -rf internal/console/ui/assets;cp -r web/dist/. internal/console/ui/
make build          # ui + go build -o bin/os ./cmd/os

# 运行:控制台 + JSON API + webhook/轮询一起
./bin/os server --port 8787 --digest off            # 开浏览器 http://127.0.0.1:8787/
./bin/os server --queue-work --queue-interval 10    # (可选)7.3 起页面建任务可由 server 自动消费

# 开发(热更,免重嵌入):vite proxy /api + /healthz → http://127.0.0.1:8787
cd web && npm run dev                               # http://127.0.0.1:5173/,后端 `os server --port 8787` 需另起
```

- **页面 → 契约**:8 页全部走真 `/api/v1`(总览 `overview` 15s / 审批三态决策 / 决策档案 / 任务中心+执行回合 /
  研发仓库+立即同步 / 知识库检索高亮 / 审计流水 / 模型端点池 token-指示+拉取+选模型),字段逐字对齐后端 json tag。
- **认证**:`OS_API_TOKEN` 启动时页面 401 → 右上弹「输入 token」(存 localStorage `os.token`),空库首次自动进入建公司页。
- **主题**:顶栏 浅色/深色/跟随系统;状态色/堆积条用 CSS 变量随主题切换;侧栏恒深色。全屏内容流体铺满(无 max-width)。
- **已知与 CLI 一致的事实**:审批/审计**全局**(无 company 参数);`overview` 的 capabilities/workflows/pending_approvals
  在空态是 JSON **null**(前端兜底);执行与队列驱动仍在后台(`--queue-work` 或 `os queue work`),页面只读展示回合记录。
- 提交前若 `internal/console/ui/index.html` 已被 dist 覆盖:`git checkout -- internal/console/ui/index.html`(占位回滚,assets 已忽略)。

## 五、工作流定义(JSON)

`os workflow add --definition` 接受一个**有序节点数组**。每个节点字段:

| 字段 | 必填 | 说明 |
|---|---|---|
| `step` | 是 | 节点标识(日志/进度显示) |
| `title` | 是 | 节点标题(生成 Task 标题) |
| `description` | 是 | 传给工具的指令(同 task create --description) |
| `tool` | 是 | `shell` / `git` / `file-read` / `file-write` / `aifix` / `engineering`(研发整包请求,认领即回合驱动 + planner 拆解,见 §4.7) |
| `agent_role` | 是 | 执行角色;**留空 = 审批门** |
| `capability` | 否 | Capability code;非空 → 按 (capability, role) 解析 Agent;空 → 公司级 role 回退 |
| `risk` | 否 | 默认 `medium`;`high` 触发审批 |
| `workspace` | 否 | 工作区目录;缺省自动建临时目录 |
| `skip` | 否 | `true` = 输入声明节点,不执行(只留审计) |

规则:
- **审批门**:`agent_role` 为空的节点 → Task 进入 `waiting_approval`,人工 approve 后直接放行(门节点无实际执行)。
- **跨 Capability**:节点声明 `capability` → 在对应 Capability 里按 role 找 Agent,Task 归属该 Capability。
- **风险触发**:`risk: high` 的节点(如 git commit 交付)无论角色都会卡审批。

一个最小示例:

```json
[
  {"step": "research",  "title": "市场研究", "tool": "file-write",
   "capability": "research", "agent_role": "market",
   "description": "write research.md\n# 研究\n……", "workspace": "/abs/path/ws"},
  {"step": "approval", "title": "审批门", "tool": "shell", "agent_role": "",
   "risk": "high", "workspace": "/abs/path/ws"},
  {"step": "delivery", "title": "交付", "tool": "git",
   "capability": "operations", "agent_role": "quality",
   "description": "git commit -am \"deliver\"", "risk": "high", "workspace": "/abs/path/ws"}
]
```

完整参考:新品发布 9 节点定义见 `docs/phase5/examples/product-launch-workflow.json`(跨 research/product/engineering/marketing/sales/operations 六大家族,含 skip 输入节点 + 两次审批门)。

## 六、权限与治理

**模型**:Policy(策略)→ Permission(权限,挂在策略下)。执行前校验,默认拒绝。

```bash
./bin/os policy add --company $CID --name "write-file" --kind allow \
  --statement "内容角色可写 workspace 文件"
./bin/os permission add --policy <policy-id> --subject coding --action write --resource file
```

| Tool | 需要的 Permission |
|---|---|
| `file-read` | `read/file` |
| `file-write` | `write/file` |
| `shell` | `execute/shell` |
| `git` | `execute/git` |
| `aifix` | `execute/aifix` |

- `subject` = Agent 的 role 字符串(如 `coding`/`market`/`quality`)。
- 无对应权限 → 任务 failed,错误含 `permission denied`。

## 七、交付约定(git)

git 工具只放行**本地操作**(init/status/add/commit/diff/log/…),网络操作(clone/pull/push/fetch)**不支持**。

关键坑:`git commit -am` **只提交已跟踪文件**。新文件不会被提交。约定做法:

```bash
# 1. 工作区先 git init 并预置业务文件骨架(占位提交一次)
cd /path/to/ws && git init -q && git add . && git commit -qm "skeleton"
# 2. 工作流里 file-write 改写这些已跟踪文件
# 3. delivery 节点 git commit -am "deliver ..." 才会带上改动
```

## 八、常见坑速查

| 现象 | 原因 / 对策 |
|---|---|
| 外键错误 `FK constraint (787)` | 传了短 ID;`--capability/--agent/--policy` 用完整 UUID |
| 任务 failed `workspace path is empty` | shell/git/file 工具都要求 workspace;`task create --workspace <dir>` |
| 文件内容 0 字节 / 文件名带 `\n` | shell 里 `\n` 是字面量;description 用单引号整段包裹 |
| `workflow run` 卡在审批门不结束 | 设计如此(run 需保持存活);**后台运行 run,前台 approve** |
| run 被杀后重跑报任务已存在 | 无断点续跑;新建一个 workflow 实例重跑 |
| `memory search 反馈` 无结果 | FTS5 trigram 需要 ≥3 字;2 字查询自动回退 LIKE,含义放宽 |
| 交付 commit 没带上新文件 | `git commit -am` 只提交已跟踪文件;先 git init + 预置骨架 |
| 任务 failed `permission denied` | 未授权;`policy add` + `permission add` 给角色授权 |
| 审批没触发 | 只有 `risk=high` 或 approval policy 才触发;节点 risk 默认 medium |
| 工程任务 failed `no … endpoint set` | engineering 家族要模型端点;配 `os endpoint add/select`,离线冒烟 `OS_ENGINE_MODE=scripted` |
| 熔断/待审批没收到飞书 | `OS_FEISHU_WEBHOOK` 未配即禁用(引擎照常转 waiting_approval);配机器人 URL 或先用 `file:///…` 验内容 |
| 每日摘要没自动发 | `os server` 需常驻且到点才发;手动验证 `--digest-now`;关定时用 `--digest off` |
| `intake sync` 报 `OS_GITHUB_TOKEN required` | 拉真 issue 需 token;离线用 `OS_ISSUE_SOURCE=fixture` + `OS_FIXTURE_ISSUES=<json 路径>` |
| 列表短 ID 拼不回去 | 外键参数一律用 create/add 输出的**完整 UUID**(列表显示的是 8 位短 ID) |
| `/api/v1` 报 401 | server 起了 `OS_API_TOKEN`;请求带 `Authorization: Bearer <token>`(/healthz 免认证) |
| `/api/v1` 报 404 not_found / 400 bad_request | 404=id 查无(`sql.ErrNoRows`);400=请求体缺必填;先看响应 `error.code/message` |
| `/api/v1` 裸奔暴露公网 | server 因收 GitHub webhook 需公网可达;**对外暴露务必设 `OS_API_TOKEN`**;未设=开放(仅可信网) |
| JSON 里时间不是字符串 | 契约 = int64 unix 秒(与 DB 一致),不是 RFC3339;字段 snake_case、无 omitempty(空字段=null) |

## 九、命令速查表

| 想做什么 | 命令 |
|---|---|
| 建公司 | `os company create --name X --vision Y` |
| 加能力域 | `os capability add --company <id> --code eng --name 工程` |
| 加 Agent | `os agent add --capability <id> --name 编码 --role coding` |
| 建任务 | `os task create --company <id> --title T --tool file-write --description '…'` |
| 跑任务 | `os task run <id>` |
| 跑队列 | `os queue work --worker w1`(或 server 带 `--queue-work` 自驱,worker=server) |
| 编排流程 | `os workflow add --company <id> --name N --definition "$(cat x.json)"` |
| 跑流程 | `os workflow run <id>`(后台) |
| 处理审批 | `os approval list` / `approve|reject|changes <id>` |
| 查审计 | `os audit list` |
| 沉淀知识 | `os memory add/list/search --company <id>` |
| 记决策 | `os decision add/list/show --company <id>` |
| 看全局(含研发部块) | `os overview --company <id>` |
| 看工具 | `os tool list` |
| 配真实模型端点 | `os endpoint add/list/models/select --company <id>`(离线 `OS_ENGINE_MODE=scripted`) |

| 给控制台/脚本读 JSON | `os server` 暴露 `/api/v1`(信封 `{ok,data}`,认证 `OS_API_TOKEN`→Bearer);契约见 design web-console.md §五 |
